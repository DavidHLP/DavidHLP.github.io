UltiCode is an online judge with Console and Management entry points. Auth, Admin, App, Submission, and Notification have separate data responsibilities. Judge Worker consumes submissions, runs Docker sandboxes, and writes results; Search Worker maintains only derived search indexes.

Its engineering interest lies in cross-service facts, delivery failures, rejudge races, expired leases, container infrastructure errors, and delivery pipelines. Failure and uncertainty become inspectable states.

UltiCode is not an LLM product, but its treatment of untrusted input, asynchronous execution, idempotency, isolation, and evidence also applies to generated code, tool calls, and long-running Agent tasks.

## Eight design highlights

| Highlight | Problem | Mechanism |
|---|---|---|
| Owner boundaries | Read/write ownership remains an oral agreement | Data owner, implementation-free contract, port/projection |
| Recoverable auditing | Business commit succeeds but cross-owner audit does not | Owner-local outbox, Redis Stream, consumer inbox, idempotency key |
| Recoverable delivery | Submission commits while the queue is unavailable | DB outbox, `FOR UPDATE SKIP LOCKED`, Streams, retry/dead-letter |
| Result fencing | A rejudge or old worker overwrites a newer result | `generation` + `attemptId` + conditional update |
| Singleton fencing | Expired worker marks completion after takeover | DB lease, monotonic `fence_token`, conditional update |
| Execution isolation | Infrastructure failures look like ordinary user runtime errors | Docker resource/security flags, seccomp, failure classification |
| Module lifecycle | Multi-context timeouts, late returns, duplicate close | opt-in, allowlist, bounded timeout, close-once handoff |
| Delivery evidence | Build success says little about dependency/image security | zero-infra static contract, Trivy, SBOM, Cosign, provenance |

## 1. Owner boundaries make write ownership explicit

Architecture documents define five Data Owners and two Workers:

| Role | Facts/writes owned | Excluded responsibility |
|---|---|---|
| Auth | Login, registration, OAuth, credentials, refresh state, RBAC, JWKS | Other owners' business tables |
| Admin | Management BFF, audit, settings, monitoring, backups, read models | App or Submission domain writes |
| App | Profiles, Problem, Contest, Solution, Forum, interactions, achievements, subscriptions | Submission results |
| Submission | Intake, judging state, generation, lease fencing, results, judge outbox | Problem, TestCase, Contest tables |
| Notification | Notifications, preferences, delivery ledger, email, Inbox, retries | Scattering notification state among business owners |
| Judge Worker | Judge Stream consumption, Problem facts, sandbox execution, verdict writes | Direct business-table writes or business HTTP entry points |
| Search Worker | `SearchDocumentChanged`, derived MeiliSearch indexes | Business-table writes or business HTTP entry points |

The default cross-boundary interface is a provider-owned contract or consumer-owned port, rather than shared Entity, Mapper, or business Service. `services/api/*` contains implementation-free contracts; `services/platform/*` is a constrained shared layer. Reusable `judge-runtime` does not automatically imply a separate process.

### Immutable fact snapshots reduce cross-owner coupling

Querying App/Auth during Submission's database write would mix remote calls, authorization boundaries, and request timing into the write path.

The intake interface accepts [`SubmissionFactsSnapshot`](https://github.com/DavidHLP/UltiCode/blob/f801a1076b2fa9aa06ce3d63821f0778b477042c/services/api/submission-api/src/main/java/com/ulticode/submission/api/dto/SubmissionFactsSnapshot.java). App's [`RemoteSubmissionWritePort`](https://github.com/DavidHLP/UltiCode/blob/f801a1076b2fa9aa06ce3d63821f0778b477042c/services/app/app-web/src/main/java/com/ulticode/modules/submission/port/adapter/RemoteSubmissionWritePort.java) first captures:

- `userId` and `userExists`;
- problem ID, title, slug, time/memory limits, and starter code;
- `capturedAtEpochMillis` and `schemaVersion`.

Submission uses `facts.admits(requestedUserId, requestedProblemId)` to check schema version, user existence, user ID, and problem ID. Origin, capture time, and interpretation version become data rather than implicit caller assumptions.

Snapshot validity periods, cross-owner revocation, and business rules still need system definitions. This is not a complete authorization or consistency proof, but it makes the write contract easier to test and audit than ad hoc remote calls inside the core transaction.

## 2. Outbox + Redis Streams turn delivery failure into state

With judge outbox enabled, submission and judging intent are stored in one database transaction:

```text
submit @Transactional
    ├── submissions: Pending
    └── judge_outbox: PENDING
             │
             ├── claim: FOR UPDATE SKIP LOCKED
             ├── atomic SET + XADD
             └── judge-workers
                    └── lease fence -> verdict
```

[`JudgeOutboxMapper`](https://github.com/DavidHLP/UltiCode/blob/f801a1076b2fa9aa06ce3d63821f0778b477042c/services/submission/src/main/java/com/ulticode/modules/submission/outbox/mapper/JudgeOutboxMapper.java) claims `PENDING` records by next retry time with `FOR UPDATE SKIP LOCKED`, preventing dispatchers from claiming the same batch. Default batch size is 50 and scheduling period is two seconds: source defaults, not throughput promises.

[`JudgeOutboxDispatcher`](https://github.com/DavidHLP/UltiCode/blob/f801a1076b2fa9aa06ce3d63821f0778b477042c/services/submission/src/main/java/com/ulticode/modules/queue/outbox/dispatcher/JudgeOutboxDispatcher.java) distinguishes:

- Missing queue provider or enqueue exception: retain retryable state.
- Malformed payload missing `problemId`, `userId`, `language`, or `code`: mark `DEAD` rather than “sent.”
- Exponential backoff, currently capped at 60 seconds.
- Real dispatch constrained by cutover watermark and shadow flags to separate migration shadow jobs from real jobs.

The Streams adapter atomically sets a deduplication key and performs `XADD` in Lua. Its key contains `submissionId:generation`, avoiding a permanent delivery hole if the process crashes between successful SETNX and XADD.

This is not exactly-once: the database transaction and external Redis operation still have a boundary. It combines durable intent, retryable delivery, message deduplication, and result fencing against duplicate or stale execution.

### PEL recovery exposes unacknowledged messages

Consumer groups start at `0-0` so entries predating group creation remain visible. Worker NACK retains the Pending Entries List (PEL). [`UnackedStreamEntriesReaper`](https://github.com/DavidHLP/UltiCode/blob/f801a1076b2fa9aa06ce3d63821f0778b477042c/services/judge-runtime/src/main/java/com/ulticode/modules/queue/outbox/reaper/UnackedStreamEntriesReaper.java) scans idle entries every ten seconds by default, reclaims at most one per sweep, and exposes PEL size, queue delay, oldest-entry age, and DLQ metrics.

The judge-stream visibility timeout is `1_800_000L` (30 minutes). This implementation parameter guarantees neither completion within 30 minutes nor HA. Reclaimed tasks still pass generation/attempt fencing; reclaiming alone grants no write authority.

## 3. `generation` + `attemptId` reject old results at the database

A submission may be rejudged, leases expire, workers restart, and Redis messages repeat. UltiCode separates:

- `generation`: logical submission/rejudge epoch.
- `attemptId`: token for one worker's execution lease.

```text
acquire lease:  id + status=Pending + generation
renew lease:    id + current_attempt_id
write verdict:  id + generation + current_attempt_id
rejudge/reaper: expected generation -> generation + 1
```

Lease, renewal, and verdict SQL in [`SubmissionMapper`](https://github.com/DavidHLP/UltiCode/blob/f801a1076b2fa9aa06ce3d63821f0778b477042c/services/submission/src/main/java/com/ulticode/modules/submission/mapper/SubmissionMapper.java) implement conditional updates. Zero affected rows means lost lease, expired generation, or competitor takeover, rather than permission to overwrite. The executor records `judge.stale_result.dropped` and ACKs safely discarded stale results.

[`SubmissionRejudgeService`](https://github.com/DavidHLP/UltiCode/blob/f801a1076b2fa9aa06ce3d63821f0778b477042c/services/submission/src/main/java/com/ulticode/submission/admin/SubmissionRejudgeService.java) and [`JudgingLeaseReaper`](https://github.com/DavidHLP/UltiCode/blob/f801a1076b2fa9aa06ce3d63821f0778b477042c/services/submission/src/main/java/com/ulticode/modules/submission/reaper/JudgingLeaseReaper.java) advance the epoch through generation CAS, then create new judging intent. Late old messages cannot satisfy the new conditions.

This concentrates final write authority into a verifiable database condition without requiring flawless single execution upstream. Its scope is Submission's database; it does not replace cross-system authorization, message durability, or business auditing.

## 4. Docker D-form isolation also classifies infrastructure errors

The D-form path in [`SandboxExecutorImpl`](https://github.com/DavidHLP/UltiCode/blob/f801a1076b2fa9aa06ce3d63821f0778b477042c/services/judge-runtime/src/main/java/com/ulticode/modules/submission/sandbox/executor/SandboxExecutorImpl.java) creates a temporary job workspace, writes read-only `input.json`, launches Docker through the lifecycle runner, and attempts cleanup in `finally`. The command includes:

```text
--network none
--cap-drop ALL
--read-only
--user 1000:1000
--security-opt no-new-privileges
--security-opt seccomp=<resolved profile>
--memory <effective limit>
--cpus <effective limit>
--pids-limit <effective limit>
--ulimit nofile=128:128
--tmpfs /tmp:rw,exec,size=64m
<workspace>:/workspace:ro
--rm
```

A seccomp-profile resolution failure produces an explicit Docker configuration error rather than silently removing the filter. Isolation is not implicitly downgraded just to make execution appear successful.

[`SandboxOutcomeClassifier`](https://github.com/DavidHLP/UltiCode/blob/f801a1076b2fa9aa06ce3d63821f0778b477042c/services/judge-runtime/src/main/java/com/ulticode/modules/submission/sandbox/SandboxOutcomeClassifier.java) separates:

- Process startup failure: launch failure.
- Exit 137: OOM.
- Exit 125: OCI configuration or Docker daemon error.
- `Cannot fork`, pids, or `RLIMIT_NPROC`: fork limit.
- Compiler errors: compile error.
- Other nonzero exits: ordinary runtime error.

A container that never starts, a bad seccomp path, or insufficient fork resources should not be reported as user-code Runtime Error. Classification makes diagnosis and retry understandable, but comprehensive sandbox-escape prevention still requires a dedicated security audit and real-environment verification.

## 5. Preview and asynchronous execution share a contract

Separate request/state/error definitions for immediate previews and long-running tasks would cause inconsistent behavior for the same code.

[`AsyncSandboxExecutor`](https://github.com/DavidHLP/UltiCode/blob/f801a1076b2fa9aa06ce3d63821f0778b477042c/services/judge-runtime/src/main/java/com/ulticode/modules/submission/runtime/async/AsyncSandboxExecutor.java) defines `submit/poll/cancel`. `ExecutionRequest` requires a job, test case, visibility, and nonempty idempotency key. The default key is `job.runId:testCase.id`; requests also receive a SHA-256 fingerprint. Different payloads for one key can be rejected as conflicts rather than reusing the wrong result.

Judge's [`CodeExecutionProvider`](https://github.com/DavidHLP/UltiCode/blob/f801a1076b2fa9aa06ce3d63821f0778b477042c/services/judge/src/main/java/com/ulticode/judge/provider/CodeExecutionProvider.java) enforces these boundaries:

- Synchronous `execute` accepts only `PUBLIC_PREVIEW`.
- Business exceptions become typed `RpcResult`, avoiding arbitrary string parsing.
- An asynchronous submission contains one test case and bounded in-memory metadata.
- Capacity is 1024 records with a 15-minute TTL; terminal completion, cancellation, or timeout reclaims them.
- Docker is the default runtime; Judge0 is an optional adapter.

Generated code, tool arguments, and long-running Agent results likewise need state machines, idempotency keys, and capacity bounds rather than an ever-growing global tool/model invocation function.

The documented gap matters: asynchronous receipts remain bounded process-local metadata; persistent idempotency across replicas/restarts is unfinished, and external Judge0 instances are not validated by default.

## 6. Quality gates separate static contracts from heavier validation

[`scripts/dev/test.sh`](https://github.com/DavidHLP/UltiCode/blob/f801a1076b2fa9aa06ce3d63821f0778b477042c/scripts/dev/test.sh) and project documentation tier checks by cost and realism:

```text
static       -> zero-infra contract checks
unit         -> unit tests, exclude IT/IntegrationTest
quick/full   -> progressively heavier local checks
integration  -> Testcontainers, DB/Redis, sandbox and owner migration
```

The CI zero-infra entry point is:

```bash
bash scripts/test/zero-infra-validation-contract.sh --static-only
```

The static path starts no Docker, databases, services, Testcontainers, Maven, or pnpm install. It checks script contracts, paths, configuration, and safety boundaries cheaply. Database, Redis, sandbox, and cross-owner behavior belong to heavier unit/integration stages. Static checks do not replace integration evidence, and integration tests do not replace production traffic evidence.

[`docker-publish.yml`](https://github.com/DavidHLP/UltiCode/blob/f801a1076b2fa9aa06ce3d63821f0778b477042c/.github/workflows/docker-publish.yml) builds a GHCR service matrix with SBOM and provenance. Trivy blocks HIGH/CRITICAL OS/library vulnerabilities through its exit code. Cosign then signs digests and verifies signatures and attestations. GHCR image names are normalized to lowercase to prevent case-related publishing failures.

These are automated delivery/security gates, not proof that CI has established system security. Actual execution records and external credentials determine whether the pipeline runs fully in a given environment.

## 7. Four lessons for LLM/Agent engineering

UltiCode handles submissions rather than prompts, but offers four direct analogies.

### 7.1 Put untrusted input through capability boundaries

Generated code, tool arguments, patches, and external pages need capability, resource, and data-scope checks, just as user code needs a sandbox. `owner + port + adapter` makes fact ownership and execution authority interface/type constraints rather than wishes in a system prompt.

### 7.2 Asynchronous work needs durable intent, idempotency, and fencing

Model tasks can time out, retry, repeat, or be cancelled. Outbox preserves intent; idempotency keys identify repeated requests; generation/attempt fences stop old workers writing new state. These responsibilities differ: no duplicate message does not imply no stale result.

### 7.3 Fact snapshots are easier to reproduce than implicit context

`SubmissionFactsSnapshot` carries request-time facts, capture time, and schema version. Agents can similarly snapshot visible resources, authorization scope, model version, input summaries, and execution policy to reduce ambiguity when one ID denotes different objects over time.

### 7.4 Failure classes determine recovery

Calling OOM, OCI errors, fork limits, and compile errors “execution failed” leaves monitoring and retry directionless. LLM systems likewise need distinct provider throttling, tool permission denial, invalid input, unparseable output, and business-result failure. Observable states are more useful than a single `FAILED`.
