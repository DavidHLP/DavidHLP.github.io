# RhineLabUI Astro 博客模板业务审查

审查日期：2026-10-10。源码基线：`main`，`b797a4c60f3ff5f8bbd560e10f5de66cbabc1ca1`。审查对象是网页博客模板，交付物为分析文档；未修改功能、未提交或部署。

## 判断与边界

当前项目已经具备 Markdown 内容、独立文章地址、RSS、站点地图、检索、收藏、TXT 导出及禁用 JavaScript 时的静态阅读。主要问题在于：从少量主题示例转向长期维护的个人博客时，阅读失败恢复、普通文章资源发布、内容增长与站点身份配置还没有形成完整体验。

> 🧠 **From Hindsight memory (Astro 博客模板迁移)** — 迁移目标是用 Astro 管理内容与页面，同时保留 Three.js 场景和原交互；历史验证记录不等于本次验证结果。本文已对照当前源码核查基础能力。

五列构图、每列至少一篇已发布文章、原生开场和自由拖动等是明确产品约束，不能当作缺陷整改。手机不应自动降低画质。以下建议均以保留这些能力为前提。

优先级：P1 表示核心阅读或发布路径存在条件性故障，应先处理；P2 表示持续使用、内容发现或运营信息不完整；P3 表示可选产品改进。本文没有证据证明存在 P0 问题。

“源码确认”表示逻辑及触发条件可直接从源码确定，不表示已经在浏览器复现。实际耗时、设备体验、缓存额度与搜索引擎表现均不作实测结论。

### B01：三维失败阻断正文阅读

**触发条件：** 浏览器允许 JavaScript，但 WebGL、模型请求失败，或启动等待的 MiSans document.fonts.load 请求拒绝。Novecento 加载失败已在 `src/boot-lettering.ts:25` 捕获并回退到固定字形，不属于本条触发条件。

`src/main.ts:62` 在三维资源加载之前添加 `interactive` 并把静态正文设为 `aria-hidden`；`src/blog.css:1` 随即隐藏静态正文。`src/main.ts:1187` 的启动流程等待模型和字体，异常分支 `src/main.ts:1219` 只提供重新连接按钮，没有恢复静态正文或切换到纯阅读。

**业务影响：** 已生成的文章内容存在，却无法被这类访问者阅读；禁用 JavaScript 的兜底不能覆盖“JavaScript 正常、三维失败”。错误提示还将资源问题统一归因于硬件加速，无法区分网络与字体失败。

**最小处理：** 首次启动失败时提供直接进入现有静态目录或初始请求文章的入口，恢复其可见性与辅助技术可访问性，并停止或释放失败的三维实例。静态正文取决于初始请求；如果以后覆盖运行期故障，应跳转当前文章独立地址或同步静态正文，不能仅解除隐藏就认定恢复当前文章。正常开场不变。

**验收场景：** 模型请求失败、WebGL 不可用、MiSans 启动字体请求拒绝分别触发时，初始请求文章仍可读，目录可打开文章，重新连接仍可用；Novecento 失败应继续走已有字形回退。

### B02：博客图片和附件没有完整进入发行包

**触发条件：** 作者将图片置于 `public/images/example.png`，在 Markdown 中使用 `/images/example.png`；附件同理，例如 `public/downloads/note.pdf`。

`scripts/build-pwa.mjs:6` 仅选入指定页面和 assets、icons、archives、licenses、fonts 及三首音频等路径；`images/` 和 `downloads/` 不在清单中。`scripts/pwa-worker.js:62` 对不在清单的请求直接退出。`scripts/package-cloudflare.mjs:26` 又使用该清单作为正式发行文件集合，而不是完整 `dist/`。

**业务影响：** 将完整 `dist/` 部署时这类资源在线可用，但不受此 Service Worker 的离线缓存保障；使用项目推荐的 Cloudflare 包装发布时，它们甚至不进入发行目录。新增自定义静态页面也需要检查是否落入这个白名单。问题不是所有图片都会丢失：位于允许的扁平 `assets/` 中的构建资源可被包含。

**最小处理：** 将“公开站点发行文件集合”和“需要预缓存的文件集合”分开确定，确保作者公开资源进入发行包；明确哪些正文资源支持离线，避免遗漏时仍笼统声称全部文章已离线就绪。

**验收场景：** 同一篇含 public 图片、构建生成图片和 PDF 链接的文章，完整 dist 与 Cloudflare 包在线行为一致；断网后按已声明范围验证。外部 URL 的资源不能自动视为离线可用。

### B03：章节定位缺少完整的交互恢复流程

`src/layouts/Terminal.astro:65` 为全部文章生成模板；`src/main.ts:589` 将选中文章模板的 HTML 复制到当前页面。独立文章的静态正文和交互正文可能含相同标题 ID，静态正文先在文档中出现且被隐藏。

**需复验的章节问题：** `src/main.ts:512` 在实际切换路径时不保留 hash；未改变路径时则不会执行 pushState，不能说直接文章地址的 hash 一定丢失。当前没有文章章节恢复流程。深链接 `/blog/文章/#章节` 和正文内 `#章节` 存在定位到隐藏节点、未定位可见正文或切换时丢失定位的风险。具体浏览器表现尚未复现。

**复查排除：** `setMode` 在 `src/main.ts:375` 先同步文章路径，再在第 408 行插入正文。不能据此断言从首页进入文章时相对 URL 按首页解析；相对图片与链接应作为验收场景，而不是已经确认的缺陷。

**最小处理：** 先复现章节问题，再给当前可见文章建立唯一、可恢复的章节目标；记录支持的正文链接和资源写法。

**验收场景：** 从首页检索进入、直接进入、文章间切换及浏览器前进后退时，正文相对链接、图片与章节链接一致。文章结果使用原生链接可改善复制链接与新标签打开，但这属于附加交互改进，不是本条的必要修复。

### B04：内容越多，每个文章页面越重

`src/layouts/Terminal.astro:9` 每次获取全部已发布文章，逐篇 render，并在每页嵌入全部正文模板；JSON 数据又携带原始正文。全部文章路由复用这个布局，PWA 还预缓存全部文章页面。

**业务影响：** 阅读一篇文章也要下载其他文章内容；设文章数为 N、全集正文大小为 S，正文在发行页面中的重复量大致随 N×S 增长，若平均正文大小相近则呈近似平方增长。实际文件大小受标记和压缩影响，不能把这个关系当作测得的下载时间。离线更新也会携带重复内容。

布局已有注释说明这是为了即时切档的有意简化，因此应登记为扩展限制，不能认定当前 40 篇短示例已经卡顿。

**最小处理：** 保留目录元数据与当前文章正文，其他正文按需获取；调整时必须保留现有全文检索（`src/main.ts:704` 使用 r.body），同时处理 JSON 原始正文与 HTML 模板两份全量内容，不能仅移除模板。如维持完整离线能力，可缓存每篇独立内容一次。先测真实内容规模，再决定实施时机，不需要先改 Three.js 模型或画质。

**验收场景：** 少量与较多长文的 HTML 大小、离线总量和切档行为对比；新增文章不使每篇页面继续复制全部正文。

### B05：读者难以判断文章的新旧与更新

`src/lib/blog.ts:5` 按档案编号排序；`src/main.ts:701` 的结果列表沿用该顺序。`src/main.ts:564` 的详情只显示科室、编目范围、相关人物和状态，没有显示 `pubDate`、`updatedDate`；标签只参与检索，没有作为浏览入口。静态文章会展示发布时间，RSS 在 `src/pages/rss.xml.ts:11` 已按发布时间倒序，不能说整个站点没有日期或新文章能力。

**业务影响：** 内容维护者可以发布和更新文章，但常规交互读者难以判断最近写了什么、旧文是否更新；`date` 编目文字也不等同于实际发布日期。现有编号必须稳定，不能靠重新编号解决排序。

**最小处理：** 在现有详情显示发布与更新日期，并在静态文章正文补充更新时间（目前仅发布日期可见）；在检索内提供最近发布的查看顺序。标签浏览按需求决定，不要求新增分类系统或改变五列。

**验收场景：** 编号较小但发布时间较新的文章可被识别；修改更新时间后交互正文与静态正文表达一致。

### B06：配置了个人博客，安装入口仍可能显示主题名称

站点标题、描述和作者由 `content/site.json` 配置；`src/layouts/Terminal.astro:28` 的 Apple 主屏幕标题固定为 Rhine Lab，当前 `public/manifest.webmanifest` 中的 name、short_name 和 description 也是固定主题值。`src/main.ts` 保留固定角色及主题文案，这本身是主题设计；问题在于没有清楚区分站点经营身份、安装身份与保留的视觉署名。

RSS 链接存在于静态 header 和 head alternate，但交互模式隐藏静态 header，交互主导航是检索、收藏和设置，未提供直接订阅入口。

**业务影响：** 模板使用者修改 site.json 后，网页标题与安装后的应用名称可能不一致；普通读者需要猜测 RSS 地址或依赖客户端自动发现。此处不要求替换原视觉或删除作者署名。

**最小处理：** 使安装名称与站点配置一致；补充可见的订阅入口，并在说明中标出哪些主题文字保留、哪些属于个人站点配置。默认 example.com 已在 README 要求修改，属于部署前置条件；可以加占位域名发布检查，但不能把模板默认值本身当作线上事故。

**验收场景：** 修改站点标题后，HTML、RSS 和安装名称一致；普通读者能从交互界面找到订阅地址。

### B07：收藏反馈与实际保存状态可能不一致

`src/main.ts:160` 从本地存储恢复编号集合，没有过滤当前已发布编号；数量显示使用 `saved.size`，结果列表则从当前 records 筛选。若某文章撤稿或删除，可能显示有收藏但列表找不到该项。

`src/main.ts:542` 更新集合后写入 localStorage，写入异常被忽略，仍提示“已加入收藏”。存储不可写时当前会话中确实收藏成功，但刷新后不能保证保留。

**业务影响：** 读者无法区分永久收藏、临时收藏和已下线文章。这里不要求账号、云同步或跨设备收藏。

**最小处理：** 数量按可访问收藏计算，或明确展示失效收藏状态；存储写入失败时说明仅本次会话有效。不要未经约定删除用户旧收藏记录。

**验收场景：** 收藏文章后将其设为草稿；模拟存储不可写；刷新前后的数量、提示与可访问文章一致。

### B08：交互切换只同步部分文章元数据

`src/layouts/Terminal.astro:32` 生成作者与文章发布日期、修改日期；`src/main.ts:508` 切换文章时只更新标题、描述、canonical 和部分 OG 字段，没有同步作者及文章日期。

**业务影响：** 从文章 A 切换到 B 后，当前 DOM 的作者和日期仍可能是 A；从首页切入文章则可能缺少文章日期。直接请求 B 的静态 HTML 是正确的，因此本条不能推出搜索引擎必然读错或排名受损。

**最小处理：** 同步当前文章对应元数据，回到首页时移除仅属于文章的字段。不要为了本条新增无需求的 SEO 框架。

**验收场景：** 不同作者、发布日期和修改日期的 A/B 之间切换，检查 DOM 与独立页面一致，回到首页无旧文章字段。

### B09：现有验证不足以证明长期博客使用场景

现有 `scripts/check-content.mjs` 检查内容字段、编号、分类、文字转义与导出，第 40 行已有中文及嵌套文章路径检查，第 44 行已有首页、文章目录与 RSS 的离线导航映射单元检查；`scripts/check-viewport.mjs` 为布局和渲染尺寸计算检查，不是浏览器截图或真机测试。`.github/workflows/astro.yml` 运行 build、content 和 viewport，没有运行 Cloudflare 包装检查。它们有价值，但不能据此证明普通 public 图片进入发行包、章节链接正常、真实安装成功或较多长文的离线更新可用。

**业务影响：** 主题示例通过检查，仍可能在作者第一次发布图文文章时出现 B02/B03。README 明确支持图片、代码块和表格，验收需要覆盖这些真实使用方式。

**最小处理：** 在后续整改时优先复用现有检查，覆盖一篇含长文、图片、表格、代码和内部章节链接的文章，以及撤稿后收藏、直接进入文章、资源失败阅读、Cloudflare 发行资源完整性。本文只列验收要求，不新增测试或声称这些场景已失败。

真实 iPhone Safari、主屏幕安装与离线读取必须单独记录；Chromium 尺寸模拟不能替代。本文未进行两者中的任何一项。

## 尚未构成必需缺陷的能力

评论、账号、云端收藏、后台 CMS、统计、全文 RSS、系列文章、分页、标签独立页面和社交分享图都是可选产品能力。当前是 Git/Markdown 驱动的静态主题模板，不能仅因未实现这些能力判定业务不完整。

`draft` 是明确的发布开关；当前没有按未来 pubDate 自动延迟发布的逻辑，也没有自动定时重建。需要定时发布时应先定义需求，不能让使用者误把日期字段当作发布控制。

内容源文件名与 archiveId 的稳定性已写入 README。需要文章改名时，再补重定向流程；没有现存改名需求，不先引入重定向系统。

资源再利用说明应清楚区分仓库代码许可、字体独立许可及来源采样。`public/audio/README.md` 已明确三个输入短音不在原创配乐 MIT 范围内，部署文档也说明 Novecento 的独立许可。这是模板分发边界，不是本文认定的侵权或法律结论；本文未做法律审查。

## 建议推进顺序

1. 先修 B01/B02，确保资源失败仍能读、作者资源真正被发布。
2. 再验证 B03，确认章节风险是否实际发生后修复，确保文章独立地址与内部章节语义一致。
3. 在现有界面完善 B05/B06/B07/B08，提升更新发现、订阅与状态可信度。
4. 用真实内容规模评估 B04，再决定正文按需读取方案；结合 B09 补必要验收。

前两步的目标是可用的博客阅读与发布闭环；后两步是持续运营。所有整改都应保留五列、原画质、原模型与交互参数。
