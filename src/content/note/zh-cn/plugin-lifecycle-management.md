## 定义
本页回答一个具体问题：在端能力不一致、网络会抖动、动作具有破坏性的前提下，如何让插件安装、升级、卸载和规则推送安全地收敛。它是控制面模型，不是已验证的容量方案；百万级规模、终端能力差异和故障恢复均是来源中的设计假设。

## 核心机制

### 1. 状态机：把意图、观测和结果分开

同一个终端—插件键至少要保留四类信息；不要用一个 `Online/Offline` 字段代替它们。

| 维度 | 含义 | 主要来源 |
| --- | --- | --- |
| `desired` | 策略要求的版本、规则或是否安装 | 控制面策略 |
| `current` | Agent 最近报告的版本与运行状态 | 合并心跳 |
| `ack` | 某次安装/升级/卸载操作是否被执行并回执 | 操作回执 |
| `failure` | 最近错误、连续失败次数和阻断原因 | 回执与失败统计 |

最小闭环是：`desired != current` 生成候选动作；候选动作先经过能力与安全检查；下发后等待 `ack`；成功才推进 `current`，失败则累加 `failure` 并决定重试或阻断。心跳超时只把观测标为逻辑离线，不等于卸载成功。

```text
desired <- policy
current <- heartbeat
ack, failure <- receipt(operation)
reconcile(desired, current, ack, failure)
```

### 2. 合并心跳：把高频观测和动作链路解耦

Agent 一次上报终端身份、OS/环境和多个插件状态；网关校验、限流后异步拆分处理。心跳只刷新观测并触发调度，不同步等待安装结果。心跳可以丢弃或降级，安装/升级链路不能因此绕过防线。

来源中的数量估算是一个说明性假设：100 万终端、每 60 秒一次心跳时，合并后约 `1,000,000 / 60 ≈ 16,667 QPS`；若每台 10 个插件分别上报则约为其 10 倍。它解释合并的方向，不是容量承诺。接入线程池和队列应有界，避免心跳堆积拖垮服务。

### 3. 幂等调度：锁只是并发闸门，不是业务事实

以 `uuid + plugin + op + targetVersion` 构造调度键；分布式锁防止并发处理，持久化的最近操作时间/状态再次拦截锁过期、重复消费和网络重试。

```text
lock:{uuid}:{plugin}:{op}:{targetVersion}
```

调度顺序：读取状态 → 检查近期是否已调度 → 检查黑名单、灰度和熔断 → 生成操作记录并下发 → 更新操作时间。相同操作的重复回执应可被安全识别，不得再次推进版本或重复触发副作用；具体操作 ID 字段是实现时需要补齐的契约。

### 4. 灰度与熔断：先限制爆炸半径，再观察结果

| 防线 | 判断维度 | 作用 |
| --- | --- | --- |
| 能力过滤 | OS、版本、架构、环境、权限 | 不向不支持的端下发 |
| 灰度 | UUID、地域、组织、OS、稳定 Hash 百分比 | 固定小范围试运行 |
| 高危灰度 | 内核、驱动、系统 Hook 的专门名单 | 比普通插件更高门槛 |
| 熔断 | 插件/版本/操作/OS 的回执失败率 | 阻断后续下发并告警 |

来源给出的 `5 分钟样本数 >= 100`、失败率 `>= 20%`、连续失败 `>= 30` 只是示例阈值；严重内核错误可立即阻断。百分比灰度必须用稳定 Hash，保证同一终端重复判断一致。

### 5. 最终一致性与恢复

接受心跳延迟、回执丢失、重复上报和版本滞后，用多次观测收敛，而不是让每次请求强同步：

1. 回执成功后更新操作日志与插件状态；失败进入重试和失败统计。
2. 心跳超时先标记 `Offline`，保留记录等待恢复；超过保留期再分批清理。
3. 恢复心跳重新比较 `desired/current`，只补发仍需要的操作。
4. OS 不兼容可进入带 TTL 的黑名单，避免每次心跳重复失败。
5. 熔断后的恢复需要人工解除或明确的重新观察窗口，不能由普通心跳偷偷绕过。

## 适用条件

- 终端数量高、心跳频率高，且 Agent 能聚合多个插件状态。
- 插件存在长期运行、版本升级、规则更新和回执需求。
- 控制面可以接受秒级状态滞后，并拥有定时补偿、审计和重试。
- 终端能力存在差异：容器、无 root、只读文件系统、Serverless 或安全加固环境需要白名单/黑名单。
- 轻量规则更新可走长连接直推；重量安装、多步骤升级可走脚本代理，两者的可用性假设不同。

## 不适用与风险

- 不能把来源中的“百万/千万级”当作压测结论；线程数、队列长、心跳周期和保留期都需按实际负载验证。
- 不能用此模型承诺强一致或实时可见；终端永久失联时只能保留待恢复/失败证据。
- 内核级插件失败可能导致崩溃、断网或大面积失联，普通灰度规则不足以覆盖其风险。
- 百分比灰度、失败率熔断和黑名单 TTL 的示例值不是跨环境通用配置。
- 只有分布式锁而没有持久状态、回执幂等和审计时，锁失效仍会造成重复副作用。

## 最小验证

1. 同一终端连续发送重复心跳：观测可刷新，但只产生一个未完成操作。
2. 两个调度节点同时处理同一 `uuid/plugin/targetVersion`：一个获得锁，另一个可观测地跳过。
3. 发送成功、重复、延迟和失败回执：版本只推进一次，失败计数与熔断统计一致。
4. 模拟心跳中断后恢复：状态先变 `Offline`，恢复后按 `desired/current` 补偿，不重复已确认操作。
5. 让灰度命中、未命中、能力不兼容和熔断四类端分别执行，验证危险操作不会绕过阻断。

## 证据与不确定性

- **来源事实**：`legacy-plugin-lifecycle-management` 描述合并心跳、状态机、锁与时间戳双重防重、能力过滤、稳定 Hash 灰度、按插件版本统计失败率、回执闭环和离线清理。
- **本页综合**：用 `desired/current/ack/failure` 统一解释这些字段，并把“心跳可降级、危险动作必须阻断”作为控制面边界。
- **未确认项**：来源没有给出生产压测、真实端能力分布、操作 ID 的线协议、阈值校准或永久离线时的产品策略。
