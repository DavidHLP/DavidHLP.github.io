这是一页面试能力综合，不是个人故事或问题清单。它回答：如何把“我做过一个项目”推进为可验证的工程判断——能指出自己的边界，解释机制与代价，并给出故障现场、指标和恢复证据。面试表达的目标不是堆技术名词，而是让项目真实性、机制正确性和生产可观测性互相印证。

## 核心机制

### 1. 三层能力模型

| 层次       | 必须说清                                           | 可验证证据                                | 常见失真                     |
| ---------- | -------------------------------------------------- | ----------------------------------------- | ---------------------------- |
| 项目真实性 | 入口、自己负责的模块、数据流和一次具体变更         | 代码路径、接口/表/消息、提交或测试边界    | 只报技术栈，无法解释失败路径 |
| 工程机制   | 为什么选缓存、队列、容器隔离或长连接；不用它会怎样 | 状态转换、限额、TTL、重试、幂等和异常契约 | 把“用了”当成“理解了”         |
| 生产证据   | 如何观测、定位、止损、回滚和复盘                   | 指标、日志、线程栈、GC/错误率、时间线     | 只说重启或“看日志”           |

三层必须形成因果链：**事实边界 → 机制与代价 → 可观察结果 → 故障动作**。无法提供证据的部分应标为参与、推断或待验证，而不是继续扩大个人职责。

### 2. 用缓存负结果证明“机制 + 边界”

缓存问题不应只回答“用了 Redis”。以不存在对象为例，完整解释应包含：

1. cache miss 才允许回源；数据库确认不存在后写入短 TTL 的 `NullValue` 占位值。
2. 读取时把占位值还原为业务 `null`，区分 key 不存在、negative hit 和真实对象。
3. 参数校验/布隆过滤器拦截随机非法 key；锁或 single-flight 处理热点回源；TTL 和主动失效控制陈旧窗口。
4. 序列化器是否认识占位对象必须实测，不能把 Spring 内部 `readResolve` 当作跨语言协议。

这比背“缓存穿透、击穿、雪崩”三个词更能证明对边界的理解。

### 3. 用性能排障证明“证据 + 恢复”

线上 CPU 或延迟故障可压缩为：

```text
症状 → 保留时间线和快照 → PID/TID → jstack/GC/方法证据
     → 判断代码、锁、GC 或下游 → 可逆止损 → 复核指标和复盘
```

高质量表达会说明：`RUNNABLE` 要看热点代码，`BLOCKED` 要看锁链，`WAITING` 要判断正常等待还是堆积，GC 线索要和分配、暂停、延迟对齐；不会把 `kill -9` 当成第一步，也不会把一次栈采样当成根因证明。

### 4. 把基础设施选择翻译成可验证机制

| 技术        | 要解释的机制                               | 生产证据                                    |
| ----------- | ------------------------------------------ | ------------------------------------------- |
| Docker 沙箱 | CPU、内存、网络、文件和执行时间隔离        | exit code、stderr、超时、容器健康和资源指标 |
| Kafka 判题  | 落库状态后异步削峰，消费者可重试/扩容      | 消息积压、重复消费、失败重试和最终状态      |
| WebSocket   | 只承担实时推送；心跳、重连和连接上限需治理 | 在线连接数、断线率、推送延迟                |
| JWT         | 签名/过期验证之外要有刷新和主动失效策略    | jti 黑名单、过期率、拒绝原因和审计          |

选择不能脱离业务约束：如果任务不耗时，队列增加的延迟与运维成本未必值得；如果没有实时推送需求，长连接不是 HTTP 的通用替代品。

## 适用条件

- 需要准备“项目深挖”或把简历上的技术点转换为可复核的工程叙述。
- 评估候选人是否能从接口/代码事实推导缓存、并发、异步和隔离机制。
- 讨论生产事故时，需要同时覆盖证据获取、风险控制、恢复和长期治理。
- 对尚未上线或未亲自负责的能力，愿意明确标注 provisional，而非虚构指标或职责。

## 不适用与风险

- 这页不是面试题答案、技术栈清单或个人经历替代品；没有真实代码/日志证据的内容只能作为待验证模型。
- `NullValue` 的行为依赖 Spring Cache 与序列化配置；不能从一个实现推广到所有 Redis 客户端。
- CPU 排障的阈值、GC 判断和 Arthas/HotSwap 行为依赖 JDK、OS、容器和工具版本；一次快照不能证明根因。
- Docker `restart: always`、Kafka 重试或 JWT 无状态都不是完整生产方案，仍需健康检查、幂等、积压治理和失效控制。
- 过度包装项目会让技术事实、权限边界和故障责任互相矛盾；优先缩小声明范围并留下验证入口。

## 最小验证

1. 为每个项目亮点画一条入口→状态/数据→副作用→失败路径的链，标记“我实现/我调用/我只观察”。
2. 对缓存亮点做三态测试：miss 回源、`NullValue` negative hit 不回源、真实值命中；再测试 TTL 或主动失效后的新数据可见性。
3. 对排障亮点做一次无破坏演练：保存负载、PID/TID、线程栈和 GC 证据，模拟判断 RUNNABLE/BLOCKED/GC，并验证一个可回滚止损动作前后指标。
4. 对异步或隔离亮点验证异常路径：重复消息、容器超时、连接断开、Token 失效；记录状态是否可重试、可告警、可恢复。
5. 面试回答结束前给出一个未确认项和下一步实验；这比无依据地声称“线上证明过”更可信。
